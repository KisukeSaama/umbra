# Audit of Umbra, 13 October 2026

Read-only review of the whole application at commit `2c3ab8b`: security,
compliance with the product rules in `AGENTS.md` and `docs/product.md`, the
domain and data layer, jobs, providers, the front end and the documentation.
The new work since the last report (bulk queue moves, queue search, the
`postponed` request status of ADR 0021, the per-series isolation of the series
sync, the Next 16.3.8 upgrade) was read line by line; the rest was re-read for
regressions. Line numbers refer to that commit. Nothing was changed as part of
the audit.

**Every finding in this document has since been fixed**, H1 in the commit
that follows this report and the rest in the one after it. The report is kept
as written, line numbers included. Where a fix took a different shape, or
stops at the edge of this repository, it says so here:

- Q1 is closed on Umbra's side: `accountOf` and `hasServerAccess` refuse an
  answer marked `HIT` or `STALE`. The gateway record itself was not changed;
  turning its cache off for `plex-tv` remains the operator's call.
- L10 cannot be enforced from here: the host firewall and the Traefik
  entrypoints are platform configuration. `docs/deployment.md` now states the
  requirement and how to check it. The sign-in caps are unchanged.
- L13 ships with a migration that closes every open poll but the newest
  before building the index, so it cannot fail on a database a race already
  left with two.
- L14 renames the session cookie to `__Host-umbra_session` in production,
  which signs everyone out once. The bundle check runs in the image build,
  since the CI build job is `docker build`. The two `docker:29` images inside
  the shared section of `.gitlab-ci.yml` are left unpinned.
- M4: a series the provider keeps refusing now fails the series step only on
  the cycles that try it, about every twelve hours, so the step's card can
  read green in between.

It follows `docs/audit-2026-09-16.md`. Every fix recorded there still holds;
the three places where the prose around a fix was left behind are listed under
documentation drift.

## The short version

There is no Critical finding, and the security surface is in good shape:
authorisation in every route and page, CSRF on all of `/api`, parameterised
SQL everywhere, the storage explorer still the best-guarded code in the tree.

What needs attention:

1. **High.** The CI audit gate now fails on two advisories published after the
   4 October upgrade, so the next pipeline will not deploy.
2. **Medium, members.** A request whose title arrives as a re-cut is never
   closed, and a request moved back from `postponed` to `accepted` tells nobody.
   The second one is the normal path of ADR 0021, not an edge case.
3. **Medium, jobs.** The isolation added to the series sync fixed one stall and
   opened two: a failing series is retried every cycle ahead of every healthy
   one, and a gateway-wide failure is no longer allowed to end the step.

## Findings

Severity: High means a visible malfunction, a blocked pipeline, or a real
security defect; Medium means wrong behaviour under conditions that will occur;
Low means hygiene, robustness or drift.

### High

**H1. The production audit gate fails, so the next pipeline stops.**
`.gitlab-ci.yml:218` runs `npm audit --omit=dev --audit-level=high`, and that
now reports two highs:

- `sharp` 0.35.4, pulled by `next` for the image optimiser, carries
  GHSA-wq5f-xc86-pv6w in its bundled librsvg. It ships in the standalone image
  and runs on every poster resize (`next.config.ts:17-27`). The vulnerable path
  is SVG decoding; the posters are TMDB JPEGs and `dangerouslyAllowSVG` is not
  set, so exposure is small, but the gate does not weigh that.
- `source-map-js` 1.2.1 (GHSA-68fv-2mgg-jv7q), through `postcss` and
  Tailwind. Build-time only.

Both have a fix within the current ranges. Fix: `npm audit fix`, then the
usual checks and a build, as the 4 October commit did.

### Medium

Requests:

- **M1. A request is never closed when its title arrives as a re-cut.**
  `closeRequestsPresentInLibrary` (`requests.ts:900-916`) and `inLibraryColumn`
  (`requests.ts:437-442`) match `l.tmdb_id = m.provider_id AND
l.cut_provider_id IS NULL` only, while `retireRequestsGoneFromLibrary`
  (`:943-944`), `matchesProviderId` and the Postgres test "is on the server
  under the id Umbra worked out for it" count `cut_provider_id = provider_id`
  as presence. A request for a series is accepted, a "Kai" lands on the server
  matched to nothing, `linkUnmatchedCuts` writes `cut_provider_id`: search and
  the title page say available, the request stays `accepted` forever, the home
  page keeps it under "coming soon", and staff can only reject it since
  `available` is not a manual move. Fix: the two-sided predicate in both
  places, with a database test next to the existing one.
- **M2. Moving a request back to a status it has held before notifies
  nobody.** `notifyRequestFollowers` uses `step: status` (`requests.ts:888`)
  and the dedup key is `kind:subject:step` (`notifications.ts:49-51`) under
  `ON CONFLICT DO NOTHING`. Accepted, postponed for lack of room, accepted
  again "the day there is room": the second `accepted` collides with the first
  and is dropped, so every follower's last word is still "waiting for room".
  The comment above `dedupKeyFor` calls the silence "the right way round",
  which held before ADR 0021 made back and forth the normal flow. Fix: a step
  unique per manual move (the status plus `updated_at`), keeping the plain
  status for the job's replays so those stay idempotent; one database test for
  accepted, postponed, accepted.
- **M3. Bulk accept keeps the stale "no room" word on postponed rows.**
  `bulkNote("accept")` returns `undefined` when the box is empty
  (`queue-moves.ts:79-80`), which keeps each row's note, while the row's own
  accept on a postponed request is `note: "fresh"` and erases it
  (`request-item.tsx:286-292`). Five postponed rows bulk-accepted move to
  "being added" still saying "no disk until November", on each follower's
  activity page and in the notification payload. That breaks the module's own
  rule that ticking a row never reaches further than pressing on it. Fix: erase
  the note when a request leaves `postponed` for `accepted` with nothing typed.

Jobs and providers:

- **M4. A series that keeps failing is retried on every cycle, ahead of the
  healthy ones.** `last_synced_at` is stamped only once every call for a series
  succeeded (`series.ts:189-197`), and `seriesDueForSync` orders `NULLS FIRST`
  with a limit of 20 (`series.ts:633-656`). A series whose details answer but
  one season endpoint 404s (common for an announced season) repeats `1 + N`
  calls 48 times a day; twenty such series take every slot and no live series
  is synced again, which is the stall `351b49a` set out to fix, moved from one
  series to twenty. `trackAcceptedSeries` (`series.ts:668-700`, `.limit(10)`,
  no order) has the same shape for a request whose `trackSeries` always throws.
  Fix: an attempt stamp on failure, read by the due query at the same cadence,
  as `enrichLibraryPosters` already does with `enriched_at`.
- **M5. The per-series catch also swallows failures of the whole gateway.**
  `jobs/index.ts:487-497` catches everything. On a 429 from Janus the loop sends
  up to nineteen more calls straight away, ignoring the `Retry-After` that
  `JANUS.md` asks to honour; on a hung gateway each series costs the 40 s client
  timeout, about thirteen minutes for the step against the worker's fifteen
  (`scripts/sync-worker.mjs:49`). Fix: catch only what belongs to one series (an
  upstream 404), and stop the loop on `RateLimitedError`, a timeout, a network
  failure or a gateway refusal; that wants a status on `UpstreamError` rather
  than matching its `detail` string.
- **M6. One transient failure during poster enrichment parks a title for a
  month.** `library.ts:330-336` stamps `enriched_at` on any error, and the retry
  is thirty days away (`:249`). One 429 or a Janus restart during a library
  sync leaves up to 120 new titles without poster, genres or score, which are
  what the picker filters on. Fix: stamp only when TMDB itself refused the
  title, and stop the loop otherwise.

Administration:

- **M7. The task queue pages over an unstable order.** `listOpenEpisodeTasks`
  orders by `air_date` alone before `LIMIT`/`OFFSET` (`series.ts:580`). A season
  released at once gives dozens of ties, and Postgres does not keep ties in the
  same order across offsets, so a task can appear on two pages and on none.
  This is the M3 of the last report in a new form. Fix: add season, episode and
  the task id as tiebreakers; `listTrackedSeries` (`:538`, title only) wants
  the same.

### Low

Requests and the queue:

- **L1.** The bulk route trusts the client's `kind`: an id sent as `ask` goes to
  `updateReportStatus` without `isAsk(reason)` (`queue-moves.ts:45`), so a
  crafted body can move a fault report through the request endpoint. No
  escalation, since the same role can do it through `/api/admin/reports/{id}`
  and transitions are checked, but the contract should be enforced server-side.
- **L2.** A non-`AppError` mid-selection rethrows (`queue-moves.ts:47-48`) after
  earlier rows were committed and notified; the client shows a generic error
  and skips `router.refresh()`, so moved rows stay ticked on screen.
- **L3.** The bulk bar labels reject `admin.requests.reject` on accepted rows,
  where the row says "Cancel" (`queue-selection.tsx:80`); and the French label
  for postpone, "Refuser temporairement" (`dictionaries.ts:1182, 1218-1219`),
  contradicts ADR 0021, which says postponing is not a refusal. "Mettre en
  attente" says what it does.
- **L4.** `isLiveRequest` (`requests.ts:41`) is exported and used nowhere.

Jobs and Janus:

- **L5.** The cycle row never receives a heartbeat, so its three-hour bound is
  measured from its start (`jobs/index.ts:118, 364`). The comment at `:267-268`
  says "the cycle beats too, through the steps it is running"; nothing does
  that. A cycle that genuinely runs long (M5 makes that likelier) is shown as
  interrupted while alive, and `finishCycle` later overwrites the failure.
- **L6.** The failure text of the series sync is cut at 500 characters
  (`jobs/index.ts:198`), which keeps about six entries and can stop inside one,
  and names series by TMDB id. A count and the first few titles would read
  better. No test covers the isolation or `describeFailure`, and the text shown
  on the sync page mixes English with the raw key `error.upstream`.
- **L7.** `janus.ts:46-51` spreads call-site headers after
  `X-Janus-Application-Id` and `X-Janus-Api-Key`, so a call site could override
  them; `JANUS.md` says they are set once. None does today. Spread them first.
- **L8.** The problem+json `detail` of a gateway refusal (401, 403, 404) is
  logged but not recorded (`janus.ts:83-100`), and the 404 message says "no API
  registered" where `JANUS.md` says it also means the record is disabled.

Security hardening (none exploitable as things stand):

- **L9.** The 64 kB body cap reads `Content-Length` only (`api.ts:96-103`); a
  chunked body is read whole first, bounded only by Next's
  `proxyClientMaxBodySize` default of 10 MB because `proxy.ts` runs on `/api`.
  Set `experimental.proxyClientMaxBodySize: "64kb"`.
- **L10.** Sign-in has a global cap of 60 pins and 300 claims a minute
  (`api/auth/plex/pin/route.ts:17-18`, `claim/route.ts:40-41`), keyed by an
  address read from `CF-Connecting-IP` (`rate-limit.ts:58-61`). If the origin
  answers outside Cloudflare, one host can forge the header and keep the bucket
  full, locking out new sign-ins. Firewall the origin to Cloudflare ranges or
  have Traefik overwrite the header, and say so in `docs/deployment.md`.
- **L11.** `markdown.ts:266` accepts `/\evil.example` as an internal link, which
  browsers read as `//evil.example`. Only staff write notes. Refuse `\` in a
  relative href.
- **L12.** `castVote` and `setPollActive` (`polls.ts:145-196, 262`) do not check
  that the note is published; activating the poll of a draft notifies every
  member (`:296`) and accepts votes on content nobody can read.
- **L13.** "One active poll" is enforced in application code (`polls.ts:226-232,
274-290`): two concurrent publishes both commit `active = true`. A partial
  unique index `ON poll ((true)) WHERE active` says it once, as the convention
  asks.
- **L14.** Smaller gaps: the session cookie has no `__Host-` prefix
  (`session.ts:53`); the ESLint guard against the schema in the browser covers
  `src/components` only and not `drizzle-orm` itself, and there is still no
  bundle assertion; `weighStorageEntries` and `openStorageVideo` do not apply
  `isLibrary` at the volume root (`storage-files.ts:228-230, 372-373`); the
  stream route has no rate limit; images are pinned by tag, not digest.

Domain and front end:

- **L15.** `recentTitles` filters `isNotNull(library_item.tmdb_id)`
  (`discovery.ts:266`) and then reads `cutProviderId ?? tmdbId`, so a re-cut
  matched to nothing never seeds the personal shelf.
- **L16.** Every season ask on an administration page calls `seasonGap`, which
  calls TMDB through Janus (`report-item.tsx:53`, `season-gap.ts:34`): up to
  twenty gateway calls per page where the `episode` table of a tracked series
  already holds the answer.

### Open question for the gateway

**Q1. The plex.tv record caches, and member tokens go through it.**
`accountOf` and `hasServerAccess` (`providers/plex-tv.ts`) send each member's
`X-Plex-Token` as a GET through the `plex-tv` slug. The gateway record reads
`cacheEnabled: true, cacheTtlSeconds: 0`. If zero means "follow the upstream's
`Cache-Control`" and the cache key ignores that header, a second sign-in could
be answered with the first person's `/api/v2/user`, admin role included, and
that payload (e-mail, `authToken`) would sit in the gateway cache, outside rule 5. This repository cannot show which it is. Either confirm that a TTL of zero
disables the cache, or turn caching off for the slug; in Umbra, refusing a
response that carries `X-Janus-Cache: HIT` or `STALE` on those two calls costs
two lines and closes it whatever the gateway does.

## What is done well

- Every finding of the 16 September report is fixed and still holds, H1 to L10,
  and the shapes chosen (the ESLint rule, the heartbeat, `DISTINCT ON`, the
  composite foreign key) were the right ones.
- The Postgres suite exists and passes: 41 tests of the rules that live in SQL,
  run for this audit against a local database.
- The bulk route is built the right way: zod caps of one to fifty items, ids
  de-duplicated, every row through the same single-row function so the
  transition check, the starting status in the `WHERE` and the notifications
  are shared rather than copied.
- Queue search escapes `\ % _`, binds the provider id, and shares one filter
  between the list and its count, so tabs and pagination agree.
- `postponed` was threaded through the check constraint, the partial unique
  index, the library close, the activity timeline and both dictionaries, and
  deliberately kept out of the live counts.
- The recorded failure detail of a provider call carries a slug, a status and a
  path, never a query string or a body.

## Test coverage

394 unit tests and 41 database tests. The Medium findings sit where those do
not reach, and most are one database test each: "a request closes when its
title arrives as a re-cut" (M1), "accepted, postponed, accepted notifies
twice" (M2), "a bulk accept of a postponed request erases its note" (M3), "a
failing series does not come back before a healthy one" (M4). Nothing
exercises the series-sync loop or `describeFailure` (L6).

## Documentation drift

- `docs/architecture.md:188` still says a run is interrupted after forty-five
  minutes; it is five minutes of silence since the 16 September fix.
- `docs/architecture.md:133` says seven steps; there are eight, and
  `membership-sweep` is not listed. `:162-164` says no account is skipped for
  the taste profile; accounts the server is no longer shared with are.
- `docs/architecture.md:268` says demoting an account ends its sessions;
  `accounts.ts:110` says it ends none (harmless, the role is read on every
  request).
- `docs/product.md:259-263` says the take-up note of a report is erased when it
  is marked fixed; `updateReportStatus` (`reports.ts:736`) clears it only on
  reopen, and the automatic closes never touch it. One of the two should give.
- `docs/product.md:40-42` says members never see how many people wait for a
  title; ADR 0016 and `title.waiting` show it on purpose.
- `docs/api.md:112` documents `409 error.alreadyVoted`, which no longer exists;
  the bulk `PATCH /api/admin/requests`, the `q` search parameter and the
  `postponed` status are not documented. `docs/product.md` describes neither
  queue search nor bulk selection.
- "Approved account", from before ADR 0014, survives in `AGENTS.md:51`,
  `announcements.ts:376` and the string at `dictionaries.ts:476`.
- Stale comments: `announcements.ts:124-125` still promises "one tally per
  poll" where `pollView` makes two or three queries; `admin/series/page.tsx:50-54`
  says the slices are cut on the page, they are cut in SQL; `taste.ts:88` says
  the counting happens in the database, it happens in JavaScript.
