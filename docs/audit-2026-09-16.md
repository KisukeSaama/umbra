# Audit of Umbra, 16 September 2026

Read-only review of the whole application at commit `5bbf587`: security,
compliance with the product rules in `AGENTS.md` and `docs/product.md`, the
domain and data layer, jobs, providers, the front end and the documentation.
Every finding below was checked against the code, and the three at the top were
reproduced rather than reasoned about. Line numbers refer to that commit.
Nothing was changed as part of the audit.

It follows `docs/audit-2026-09-10.md`, whose findings were fixed six days ago.
Those fixes hold, with one exception named as H1 below: the report of 10
September records it as fixed and it never was.

**Every finding in this document has since been fixed**, in the commit that
follows it on this branch. The report is kept as it was written, line numbers
included, because it is the record of what was wrong and why. Three fixes took
a different shape from the one suggested here, and each says so where it
changed:

- H1 asked for `import "server-only"` in the schema. `drizzle-kit` loads that
  file outside any React graph to generate the migrations and the package
  throws there, so the guard is an ESLint rule over `src/components` instead,
  which refuses a value import of the schema and allows a type.
- H3 asked for a closing rule of its own for a re-cut, or for the
  documentation to admit the report is closed as refused. Neither: there is no
  way to know how many episodes a Kai or a Yabai has, so nothing can count one,
  and the manual close is handed back instead. `isSettledByJob` reads the place
  as well as the reason, and the button appears exactly where no job will ever
  reach the row, which also covers the series nobody put under watch.
- M5 asked for `job_state.cursor` to be read as a heartbeat. Only the steps
  that report progress write it, so a step that walks quietly would still have
  been declared interrupted. `job_run` carries a `heartbeat_at` the runner
  stamps every fifteen seconds instead, whatever the step does.

Two things were done beyond what is written below, both in the same family as
M1 and M2: a card now links by the id its title answers to rather than by the
media server's, which pointed a re-cut's card at the series it had been
mistaken for; and the vote's option is tied to its poll by a composite foreign
key, which is L7 with its migration rather than a note.

## The short version

The code is in the shape the last audit left it in. Authorisation, the storage
explorer, the CSRF and policy layer, the library sweep and the request
lifecycle all hold, and the database-backed test suite that commit added is the
right answer to what the last report could not reach. There is no Critical
finding this time.

What is left is three things that are broken rather than fragile, and they
cluster around reports:

1. **High.** The Drizzle schema and the ORM are in the browser bundle. The
   10 September report closed this and the code never changed.
2. **High.** An ask for the rest of a season can never be closed: no job can
   settle it and the administration is not offered the button.
3. **High.** Every report a re-cut can carry is the same dead end, and a re-cut
   can carry nothing else.

Then the Medium items, all of them a variation on one theme: the rule that a
re-cut is reached through `cut_provider_id` is applied in three reads and
skipped in four others.

## Findings

Severity: High means a visible malfunction, a queue that cannot be worked, or a
real bundle defect; Medium means wrong behaviour under conditions that will
occur; Low means hygiene, robustness or drift.

### High

**H1. The Drizzle schema and the ORM are shipped to the browser.**
`src/components/admin/announcement-form.tsx:25-26`, a `"use client"` file,
value-imports `ANNOUNCEMENT_CATEGORIES` and `EMBED_RATIOS` from
`@/lib/db/schema`, which imports `drizzle-orm` and `drizzle-orm/pg-core`
(`schema.ts:1`). Confirmed in this build: `.next/static/chunks/1r-en74ebijl6.js`
is 115 KB and contains `PgTable`, `drizzle-orm`, `media_request_active_idx` and
`report_active_idx`. Every index name and column name of the database is served
to any signed-in browser that loads the announcements page.

This is H4 of the 10 September audit word for word. That report states the
finding was fixed; `git show 22a80fb` leaves both the import and `schema.ts`
untouched, and `EMBED_RATIOS` was added to the same import afterwards
(`107e7ce`). Nothing regressed: the fix was never applied.

Fix, as it was written then and still stands: move the two lists and their
types to a dependency-free module, re-export them from `schema.ts`, and add
`import "server-only"` to `schema.ts` so the next one fails the build instead of
the bundle.

**H2. "The rest of this season is missing" can never be closed.**
`reasonsFor("season")` includes `missing_episode` (`reasons.ts:38-45`), and a
season-level ask is exactly that reason with `episode_number` left null;
`reasonKey` has a plural wording for it (`reasons.ts:180-186`). Nothing can
close it:

- `closeReportsSolvedByLibrary` (`reports.ts:805-818`) matches
  `ep.episode_number = r.episode_number`, and `r.episode_number` is null, so the
  `EXISTS` is never true whatever arrives on the server;
- `closeReportsSolvedByCalendar` (`reports.ts:838-866`) answers `missing_season`
  and `series_outdated` only;
- by hand is refused too: `isAutoClosable("missing_episode")` is true, so
  `nextStatuses` strips `resolved` from every move (`reasons.ts:254`), and the
  administration renders its buttons from that list
  (`admin/report-item.tsx:112`).

What is left is `rejected` and `duplicate`. A member asks for the eight episodes
missing from a season, the staff fetch all eight, and the only way to take the
row off the queue is to tell them it was refused. `docs/product.md` says these
"close themselves when the rest arrives".

Fix: give the library rule the season case, `r.episode_number IS NULL` and a
count of what the calendar holds for that season against what the index does,
next to the `missing_season` branch that already does exactly this in
`closeReportsSolvedByCalendar`.

**H3. Every report on a re-cut is the same dead end, and it is the only report a
re-cut can carry.** `CUT_REASONS` is `missing_episode` and `series_outdated`
(`reasons.ts:157-160`), and `createReport` refuses a season or an episode number
on a re-cut (`reports.ts:111-115`), so both arrive with null in both columns.

- `missing_episode` with two nulls: H2, doubled;
- `series_outdated`: `closeReportsSolvedByCalendar` joins `tracked_series`, and
  a re-cut is never tracked (`trackSeries` refuses one, `series.ts:60-61`,
  which is the documented rule), so the `FROM` never matches;
- `resolved` is filtered out of the manual moves for both reasons.

So the one gesture the product leaves a member on a re-cut produces a row the
administration can only refuse. `docs/product.md:117-118` says the opposite:
"Both are asks, so they close themselves when the rest arrives."

Fix: decide it, and say so in the same place. Either a closing rule of their own
(a re-cut has no calendar, so the only honest one is by hand), which means
exempting a report with no season and no episode from the `isAutoClosable`
filter; or leave the filter and admit in `docs/product.md` that a re-cut report
is closed as refused.

### Medium

Re-cuts, everywhere the rule was not applied:

- **M1. The season ladder of a series the server matched to the wrong title
  counts the re-cut's episodes.** `episodeCountsBySeason`, `seasonsOnServer` and
  `episodesOnServer` (`library.ts:650-710`) join
  `show.tmdb_id = ${providerId}` with no `cut_provider_id IS NULL`, which is
  precisely the guard `matchesProviderId` exists to apply and whose own comment
  says the three reads "must stay the same". The documented case is real: the
  server files "Black Clover Kai" as "The Forsyte Saga", `linkUnmatchedCuts`
  writes `cut_provider_id` and leaves the wrong `tmdb_id` in place, and from
  then on the page of the wrong series counts the re-cut's episodes as its own.
  It travels: `seasonStates` (`catalog.ts:412`) feeds the ladder, the "is this
  season released" refusal in `createReport`, `isSeasonMissing` on the title
  page, and `GET /api/library/search`.
- **M2. The picker's "already here" half misses a re-cut and can name the wrong
  title.** `availableByProviderIds` (`library.ts:864`) and the exclusion list in
  `randomAvailableByGenres` read `tmdb_id` alone rather than
  `matchesAnyProviderId`. A re-cut the server matched to nothing is absent from
  both, so the picker offers a title the server holds; one matched elsewhere is
  returned under the wrong provider id.

Jobs and the administration:

- **M3. The task queue stops at two hundred and does not say so.**
  `listOpenEpisodeTasks` caps at 200 (`series.ts:572`) and
  `admin/series/page.tsx:69-82` pages that array in memory, so the total above
  the list (`:183`) is `min(real, 200)` and everything past it is invisible with
  no sign that it exists. The comment on the cap says a catch-up "can raise
  hundreds of these", which is the case that hides them. Page in SQL, as every
  other administration list now does, and count separately.
- **M4. The synchronisation page loses sight of the disk walk.** `jobStatus`
  reads the last fifty `job_run` rows for every step at once
  (`jobs/index.ts:582`). A cycle writes eight, so the window is about six
  cycles, three hours at the default interval, while `storage-scan` runs every
  six. Half the time the card shows no last run, no duration and no item count
  for it, although `job_state` still carries the success date. One row per step,
  or `DISTINCT ON (job_name)`.
- **M5. A long step is declared interrupted while it is still running.**
  `closeStaleRuns` fails any run older than forty-five minutes
  (`jobs/index.ts:92`, `:229-248`) and is called from `runJob`, `runningJob` and
  `runStorageScan`. A first walk of a large library, or a `library-sync` on one,
  can exceed that: the row is marked failed, the page says the step failed, and
  the button will happily start a second walk over the first. The cycle's own
  lock covers the scheduled path (three hours) but not the two buttons. Bound it
  by a heartbeat the step writes, which `job_state.cursor` already is, rather
  than by the start time.
- **M6. A poll is read four times over per note.** `pollView` selects the poll,
  groups the tally, reads the visitor's vote and calls `countAccounts()`
  (`polls.ts:69-117`); `withPolls` calls it once per poll of the page
  (`announcements.ts:143-158`), so the feed costs a `count(*)` over `account`
  per note carrying a question. The comment above `withPolls` claims "two round
  trips plus one tally per poll". Read the member count once per page and pass
  it down.

### Low

- **L1.** `JANUS.md:27, 55, 105, 106` carries four em dashes and two arrows,
  against rule 7, which says "anywhere: code, comments, documentation". The
  10 September audit noted the same for the generated block of `AGENTS.md`,
  which has a stated exception; this file has none.
- **L2.** Thirty-five files are not Prettier-formatted, fourteen of them
  generated `drizzle/meta` snapshots. There is no `.prettierignore`, and
  `format:check` is still absent from the "Before you finish" list in
  `AGENTS.md`, which is why the number has grown from nine.
- **L3.** `deploy/app.env` says the storage path "is read-only inside the
  container" while `deploy/compose.yml` mounts `${MEDIA_ROOT}` as `rw`, as ADR
  0012 requires. One of the two sentences is from before deletion existed.
- **L4.** `docs/api.md:194` still says `DELETE /api/admin/series/{id}` answers
  409 while a request for the series is accepted. `untrackSeries`
  (`series.ts:96-112`) now stamps `untracked_at` in the same transaction and
  succeeds.
- **L5.** `taste.ts:168` is a doc comment with nothing under it, left by the
  removal of `hasTasteProfile`.
- **L6.** `withdrawReport` deletes the member's notifications for the report
  whether or not anything was withdrawn (`reports.ts:361-366`), where
  `withdrawRequest` guards the same branch on `dropped OR unfollowed`
  (`requests.ts:288-295`). Harmless, but the two should read alike.
- **L7.** Nothing in the database ties `vote.option_id` to `vote.poll_id`:
  `castVote` checks it in application code (`polls.ts:142-147`), which is the
  read-then-write the project's own convention keeps out of everything else. A
  composite foreign key on `poll_option (id, poll_id)` would say it once.
- **L8.** `key={index}` on rows that are added and removed:
  `announcement-form.tsx:424` (poll options) and `search-site-panel.tsx:254`
  (fixed arguments). The values are controlled, so this costs focus and not
  data, but it is the one place the pattern actually bites.
- **L9.** `/request` exports no metadata, alone among the pages now that
  `generateMetadata` is everywhere else.
- **L10.** `checkRate` walks the whole window map on every call
  (`rate-limit.ts:26-29`). Fine at this size, and worth a comment saying so
  rather than a reader working it out.

## What is done well

- The whole of the 10 September report except H1 is genuinely fixed, and fixed
  the way it was described: `z.stringbool()` with a test, the transition tables
  for requests and reports with the starting status repeated in the `WHERE`, the
  page walk measured in raw rows with `MAX_PAGES` as an error, presence that can
  go back to false, the enrichment stamp, the transactions around a note and its
  poll, the nonce policy, the session and stream caps, the pool timeouts, the
  advisory lock around migrations.
- `tests/db/` is the answer to the last report's closing paragraph: the rules
  that live in SQL are now asserted against a real Postgres.
- The storage explorer remains the best-guarded code here: two containment
  checks, an `lstat` at every hop, links never followed, the non-library names
  refused on the path and not only in the listing, deletion refused at the root.
- Authorisation is checked in every page rather than in the layout above it, and
  every member mutation is scoped by `account_id` inside the SQL.
- No `sql.raw` anywhere, every template parameterised, `ilike` patterns escaped,
  markdown parsed to typed nodes with no HTML string on the path, embeds reduced
  to an https address and a shape.
- The schema and the migrations do not drift: `drizzle-kit generate` finds
  nothing to write.

## Test coverage

372 tests over the pure rules and the parsers, plus a Postgres suite for what
lives in SQL, skipped unless `UMBRA_TEST_DATABASE_URL` names a database. It was
not run here, so this audit says nothing about whether it passes.

The three High findings sit in the two places no test reaches: a client import
(a bundle assertion would catch H1: no chunk under `.next/static` may contain
`PgTable`) and the closing rules of a report. H2 and H3 are one test each
against the Postgres harness, "an ask on a season closes when the season
arrives" and "a report on a re-cut can be closed", and both would have failed
the day they were written.

## Documentation drift

- `docs/audit-2026-09-10.md` states that every finding in it was fixed. H4 was
  not. The report is kept as written, which is right, but the claim at the top
  of it is now false and should say which one it missed.
- `docs/product.md:117-118` promises that a re-cut's reports close themselves.
  They cannot (H3).
- `docs/api.md:194`, the series deletion conflict that no longer exists (L4).
- `deploy/app.env`, the read-only media path (L3).
